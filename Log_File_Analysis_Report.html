Counting 404 Errors and Identifying Peak Failure Times Using Hadoop & PySpark

Final Project Report — Group IDK ---

1. Objective

This project analyzes a large web server access log to:
  • Count the total number of "404 Not Found" errors
  • Identify the time of day when failures happen most often
    • ...using a distributed processing pipeline built on Hadoop (HDFS) for storage and Apache PySpark for parallel processing.

    2. Methodology / Pipeline

  • Raw server logs are stored in Hadoop Distributed File System (HDFS), which splits and replicates massive log files across cluster nodes for fault-tolerant, scalable storage.
  • PySpark reads the log file as a distributed DataFrame and parses each line with a regular expression (Common Log Format) into structured fields: IP, timestamp, HTTP method, path, status code, and response size.
  • Malformed lines are filtered out, and the cleaned DataFrame is cached in memory since it is queried repeatedly.
  • Spark's groupBy/aggregate operations count 404 occurrences overall, by hour of day, by day of week, and by endpoint (path).
  • Final aggregated results (small enough to fit in memory) are converted to Pandas and visualized with Matplotlib/Seaborn, and exported to CSV.

    9. Key Findings

  • Out of 200,000 total requests, 43,153 (21.58%) returned a 404 error — a notably high rate for a production system.
  • The single worst hour for failures is 3:00–4:00 AM, with roughly 3.5–4x the errors seen during quiet daytime hours.
  • Three endpoints — /admin/login, /old-promo-page, and /deprecated-api/v1 — are responsible for the overnight spike, consistent with automated scanners probing for an admin panel and hitting deprecated pages.
  • Daytime 404 spikes (09:00–11:00, 14:00–15:00, 20:00–21:00) align with normal peak business-hour traffic, most likely caused by broken links or outdated bookmarks.

    • 10. Recommendations

  • Remove or permanently redirect (301) /old-promo-page and /deprecated-api/v1 to eliminate a large share of 404s immediately.
  • Investigate and rate-limit the source IPs repeatedly hitting /admin/login overnight — consistent with a brute-force/reconnaissance scan.
  • Set up a recurring PySpark job to continuously monitor the 404 rate and alert if it exceeds a defined threshold.
  • Store aggregated results as partitioned Parquet files on HDFS for fast historical querying by a dashboard tool.
